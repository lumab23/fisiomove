# B05: integração proposta para Luma

Registrar app.modules.workouts.router.router em app/api/router.py
(api_router.include_router(workouts_router)). Não altera a especificação de
migração da B04; nenhuma tabela adicional. Patch separado em b05-routing.patch.

Cada criação/edição gera revisão nova. Publicar copia a revisão rascunho em
nova revisão com published_at; revisões publicadas nunca são modificadas.
Editar publicado move o agregado a draft e exige nova publicação: o paciente
não vê o rascunho nem recebe esse treino até republicação. Arquivar preserva
revisões e itens; a operação é idempotente. Edição/publicação de arquivado é 409.
PATCH ausente preserva instruções; null limpa instruções; itens, se enviados,
substituem a lista inteira e não aceitam null. Posições contíguas começam em 1.

As mutações bloqueiam a linha do agregado com SELECT FOR UPDATE no PostgreSQL,
serializando números de revisão concorrentes. SQLite testa a lógica e a
persistência, mas não comprova bloqueio concorrente PostgreSQL.

WorkoutService.published_snapshot(user, workout_id, revision_id) fornece a B07
um dicionário independente com revisão publicada autorizada e itens/snapshot
fixados, inclusive após arquivamento. Não é endpoint e não recebe identidade do
cliente. B07 ainda deve validar a elegibilidade de novas sessões. Nenhum módulo
de sessões, progresso ou conquistas foi alterado. A regra e o snapshot do
exercício ficam fixados no item; editar sem substituir itens preserva esses dados.

Verificação após integração de rotas/modelos/migração: autenticar profissional,
criar paciente/vínculo via B03, cadastrar somente exercício aprovado, criar
POST /api/v1/patients/{id}/workouts; GET /api/v1/workouts/{id}; PATCH o mesmo
recurso; POST .../publish; entrar como paciente com senha trocada e consultar
GET /api/v1/me/workouts; arquivar via POST .../archive e confirmar lista vazia.
Outro profissional deve receber 404; paciente deve receber 403 nas mutações e
404 ao consultar rascunhos/arquivados. Listas seguem page/page_size.
